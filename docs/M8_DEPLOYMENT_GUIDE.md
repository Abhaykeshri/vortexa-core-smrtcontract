# M8 Deployment Guide

This runbook is intentionally non-custodial: it documents the workflow but does not authorize a broadcast.

## 1. Populate reviewed network configuration

Update `script/NetworkConfigs.s.sol` with verified values for:

- deployed `PriceGuard` and `ShapeLibrary`;
- governance Safe (at least 3-of-5), restricted executor, guardian Safe (at least 2-of-3), and treasury;
- the Zap address. It is immutable in SwapExecutor, and VaultFactory pins the executor, so a graph deployed without it can never add the M9 Zap. `DeployM8` refuses mainnet without it; production deployment belongs to the M11 script, which deploys the Zap in the same nonce-predicted sequence. `address(0)` is for testnets only;
- initial fee and mutable fee cap;
- approved ETH/USDC vault deposit cap;
- after deployment: TimelockController, FeeCollector, three strategies, SwapExecutor, Vault implementation, VaultFactory, and VaultLens.

Do not source a contract address from an environment variable. Unknown addresses stay `address(0)`, which intentionally prevents deployment or final verification.

Confirm PriceGuard already has a valid, live configuration for every pool that will be allowlisted. The deployment script does not invent oracle or business-policy values.

## 2. Review the deterministic sequence

`DeployM8.s.sol` predicts the factory at the deployer's starting nonce plus seven and deploys:

1. TimelockController
2. FeeCollector
3. NormalLPStrategy
4. BuyTheDipStrategy
5. SellThePumpStrategy
6. SwapExecutor
7. Vault implementation
8. VaultFactory at the predicted address
9. VaultLens

The transaction reverts if the starting nonce changes or the deployed factory differs from the prediction. Do not insert another deployment into this sequence.

The script then registers the strategies, optionally sets the guardian and ETH/USDC pool rule, nominates the timelock as owner of Factory/Collector/PriceGuard, and removes the deployer's Timelock admin role. Ownership is not yet accepted.

## 3. Dry-run and simulate

With reviewed configuration and the intended sender selected in Foundry, run a simulation without `--broadcast` first:

```text
forge script script/DeployM8.s.sol:DeployM8 --rpc-url <reviewed-rpc> -vvvv
```

Record and independently verify every predicted/deployed address, constructor argument, role, fee, cap, recipient, and pool rule. Have a second reviewer compare the output with `NetworkConfigs.s.sol`.

Only after explicit authorization, simulate the exact Safe/broadcast transaction bundle through the chosen operations tooling. This repository does not store private keys.

## 4. Record deployed addresses

Write the verified deployed addresses back into `NetworkConfigs.s.sol`, including all three strategies. Rebuild and rerun tests. Do not proceed while any required final address is zero.

## 5. Schedule ownership acceptance

The governance Safe must call the batch generated by the command below. When the proposer is a Safe (always on mainnet), the script cannot broadcast for it; it prints the exact `scheduleBatch` transaction (target and calldata) and the operation id for the Safe owners to propose. An EOA proposer (testnets) broadcasts directly.

```text
forge script script/ScheduleM8Handover.s.sol:ScheduleM8Handover --rpc-url <reviewed-rpc> -vvvv
```

The batch calls `acceptOwnership()` on VaultFactory, FeeCollector, and PriceGuard. On mainnet, `getMinDelay()` must be at least 48 hours. The governance Safe has proposer/canceller roles; execution is not open to `address(0)`.

## 6. Execute after the delay

After the operation is ready, the explicitly configured executor executes the identical batch generated by the command below (a Safe executor gets the exact `executeBatch` transaction printed instead):

```text
forge script script/ExecuteM8Handover.s.sol:ExecuteM8Handover --rpc-url <reviewed-rpc> -vvvv
```

Use the same reviewed configuration and salt. Unauthorized callers must fail.

## 7. Run read-only post-deploy checks

```text
forge script script/PostDeployM8Check.s.sol:PostDeployM8Check --rpc-url <reviewed-rpc> -vvvv
```

The check verifies code presence, final ownership, treasury, implementation and dependency identities, Lens wiring, fees, guardian, optional strategy addresses, timelock delay, proposer/executor roles, closed execution, the configured ETH/USDC pool rule, that no ownership transfer is pending, and that the deployer holds no role anywhere (Timelock admin, proposer, canceller or executor; keeper; guardian; treasury). Record the deployer in `NetworkConfigs.s.sol` (`deploymentOwner`) first: an unset value fails the check instead of skipping it.

Also verify manually:

- the governance Safe is really configured 3-of-5;
- the guardian Safe is really configured 2-of-3;
- the restricted executor is operational and not `address(0)`;
- no deployer address retains ownership or Timelock admin;
- PriceGuard reference sources are fresh and correctly oriented;
- pool rules and deposit caps match approved governance records;
- `isRouter` and `setRouter` do not exist;
- implementation and module bytecode match the audited build.

## 8. Fork and smoke verification

Run the complete fork profile against an archive-capable endpoint at a block after deployment. Create a small-cap test vault only if governance explicitly authorizes the state-changing transaction. Before user deposits, test deterministic prediction, clone initialization, Lens reads, pause/unpause governance, keeper access, fee forwarding, and an emergency cancellation workflow.

## Rollback boundaries

The deployment transaction is atomic, but completed deployments are immutable. Until the timelock accepts ownership (at least 48 hours on mainnet), the deployer still owns VaultFactory, FeeCollector and PriceGuard and can call every owner function: keepers, guardian, pool rules, fees, collector, strategies, implementation, PriceGuard pair configurations, and a new ownership nomination. Keep the deployer key offline for the whole window, watch the contracts' events until the handover executes, and run `PostDeployM8Check`: it fails if the deployer kept any role, if an ownership transfer is still pending, or if the configured ETH/USDC pool rule changed. After acceptance, changes require the timelock. A bad implementation or immutable dependency cannot be repaired for an existing clone—deploy a corrected implementation/factory path for future vaults and leave existing vault funds withdrawable.
