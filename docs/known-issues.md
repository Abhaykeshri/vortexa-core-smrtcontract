# Known Issues

- M0-M9 protocol code and M10 security validation are present, but the repository is not cleared for production deployment or use with user funds. The final M11 deployment configuration is not implemented; production addresses that are not yet known remain `address(0)` in `script/NetworkConfigs.s.sol`; monitoring, operations, the required long-duration property run, independent review, and signed freeze process remain outstanding.
- The `Vault` constructor retains its ShapeLibrary parameter and nonzero check for deployment-interface compatibility, but production strategy contracts now own and call their immutable ShapeLibrary dependency. The Vault no longer exposes a `shapes()` getter.
- The optimized Vault runtime is close to the EIP-170 ceiling. The M10 baseline measures 24,264 of 24,576 bytes (312 bytes headroom). Future additions should remain modular and must rerun `forge build --sizes`.
- M2 contains the generic `PriceGuard`, but production deployment still requires chain-specific addresses, feed selection, pool-key configuration, and fork validation.
- The guide's displayed tick coefficient expression says floor, but literal floor coefficients do not match the pinned Uniswap v4 `TickMath` values. The pinned source states nearest-integer coefficient rounding; M1 follows that convention and verifies exact outputs differentially.
- Aderyn 0.6.8 was executed locally via WSL with all 88 detectors and reported 0 High findings and 0 Low findings. Reviewed false positives and accepted design choices use detector-specific, line-scoped annotations documented in `docs/ADERYN_TRIAGE.md`. This is a static-analysis run, not an independent audit.
- Slither is not installed in the local PowerShell environment used for this review. Hosted CI results are not available until this directory is connected to a remote repository.
- GitHub branch protection (two reviewers and signed commits) is a repository-host setting and cannot be enforced in a local repository without a GitHub remote and administrative access.

## Found by the M0-M2 audit (see `docs/M2_AUDIT_REPORT.md`)

- `PriceGuard` inherits OpenZeppelin's `renounceOwnership`. If the timelock ever renounces, `setPairConfig` is frozen forever: existing configurations keep working, but a dead feed can never be replaced. Overriding `renounceOwnership` to revert is recommended; it is pinned by `test_known_issue_renounce_ownership_freezes_configuration_but_not_reads` until decided.
- `CurrencyLib.transfer` of native currency to `address(0)` succeeds and burns the ETH (ERC-20 transfers to zero revert). Every call site (vault, zap, fee collector) must reject a zero receiver before calling it. Pinned by `test_known_issue_native_transfer_to_zero_address_burns_funds`.
- `CurrencyLib.transfer` reports success for fee-on-transfer tokens even though the recipient receives less. Call sites must measure balance deltas (the guide already requires this for deposits and zaps).
- `CurrencyLib.balanceOfSelf` for native currency includes `msg.value` inside a payable call. Callers snapshotting idle ETH must subtract it.
- `isPriceTrusted` reports the deviation floored to whole basis points, so the real deviation at the trust boundary can be up to `maxDeviationBps + 0.9999` bp. One Uniswap tick (about 0.9999 bp) is also below this resolution, so a single-tick error in a TWAP reference cannot be seen through `devBps`; `_floorDivTick` is therefore tested directly.
- A reference contract that returns data that cannot be ABI-decoded makes `isPriceTrusted` and `setPairConfig` revert instead of returning false. This fails closed for every consumer (deposits and rebalances revert, withdrawals never call `PriceGuard`) and can only come from an owner-approved feed or pool.
- A reference contract that violates the static call context (for example by writing storage) burns the gas forwarded to it. Again only reachable through an owner-approved reference.
- Chainlink `minAnswer` and `maxAnswer` are inclusive. To reject a clamped answer, the owner must set `minAnswer` strictly above (and `maxAnswer` strictly below) the feed's own built-in clamp values.
- While the primary Chainlink answer is unavailable, a V3 TWAP fallback that is manipulated for a whole window in step with the V4 pool is accepted (guide 12.4 "Thin v3 fallback manipulated"). A fresh Chainlink answer always takes precedence and closes the gap. Pinned by `test_known_issue_fallback_can_be_fooled_only_while_chainlink_is_down`.
- A single USD feed treats the quote token as exactly one dollar. A stablecoin depeg smaller than `maxDeviationBps` is not detected.
- Token decimals are cached when the configuration is set. If a token's `decimals()` later changes, the cached value keeps being used until the owner reconfigures the pool, and reconfiguration then rejects the pair if the pool price no longer matches.
- Hosted CI does not exist yet (no `.github`). The checks the guide assigns to CI for `src/` (exact pragma, SPDX, forbidden imports and constructs, NatSpec) now run inside `forge test` via `test/unit/SrcPolicy.t.sol`; Slither, Aderyn, coverage floor and gas snapshots still need a pipeline.

## Found by the M3 audit (see `docs/M3_AUDIT_REPORT.md`)

No functional defect was found in `ShapeLibrary`. The following behaviours follow the developer guide but are easy to misread, and are pinned by tests so that any change is deliberate.

- The last band absorbs the whole remainder of the range, up to `bandCount - 1` extra tick spacings. For a range barely wider than the band count the last band is several times wider than the others while carrying the same relative weight (nine spacings over five bands give widths 1, 1, 1, 1, 5). The factory or UI should reject ranges narrower than about 40 spacings per band (distortion at most 10%). Pinned by `test_known_behaviour_last_band_can_be_several_times_wider` and `test_remainder_is_bounded_by_band_count_minus_one`.
- The uniform fallback used when a range has fewer spacings than the preset's band count gives its remainder basis points to the earliest bands (for three bands `3334, 3333, 3333`), so those weights are not symmetric. The difference is one basis point.
- `computeBands` does not validate that the center lies inside the usable range: a request whose window overlaps the usable range is clamped and served even if the center is outside it. The factory must validate centers and ticks (guide 10.1). Pinned by `test_center_outside_the_usable_range_is_clamped_not_rejected`.
- Tick spacings above Uniswap v4's maximum of 32,767 are accepted by the library (they leave no usable range beyond tick zero and normally end in `EmptyRange`). Uniswap cannot create such pools, so this is harmless.
- A request whose aligned lower and upper edges coincide (a zero width on an aligned center) reverts with `EmptyRange` instead of returning a zero-width band. A misaligned center expands to one full spacing. Interfaces must handle both.
- The single-tick preset anchors at the center rounded down, so it is not mirror symmetric (a center of 5 with spacing 10 starts at 0, the mirrored center of -5 starts at -10).
- The vault must repeat the band checks on whatever the shape library returns (guide 5.3). A reusable checker with negative controls for every kind of tampering lives in `test/utils/BandRules.sol`; M4 should port the same rules into `Vault`.

## Found by the M2/M3 re-audit (see `docs/REAUDIT_M2_M3.md`)

No new defect was found in `src/`. The items below are prerequisites and limits for later milestones.

- **Deposit planning (M4).** Planning a deposit by scaling a unit liquidity with the band weights can need slightly more than the budget (witness: 1.5e-18 relative), because the unit amounts are rounded down once and then multiplied up. Rounding the common scale to 1e18 fixed point wastes up to 2e-5 of the budget at extreme prices. Use the guide's method with the scale kept as a ratio: allot each band `unitAmount * weight * budget / total` in one `mulDiv`, then call `liquidityForAmounts` per band. `test/utils/DepositPlanner.sol` is the reference; the hazards are pinned by `test_naive_unit_scaling_overshoots_a_budget_but_the_guide_method_does_not` and `test_rounding_the_scale_to_fixed_point_wastes_budget_at_extreme_prices`.
- **`liquidityForAmounts` precision at extreme low prices (inherited from Uniswap).** It uses `floor(sa * sb / 2^96)`, which is tiny when the raw price is below about 1e-20 (tick below about -460,000), costing up to 50% of the token0 budget (the rest is refunded). Our function equals Uniswap's `LiquidityAmounts` on the witness, so this is not an M1 defect. Pinned by `test_known_issue_liquidity_for_amounts_loses_precision_at_extreme_low_prices`.
- **Integer granularity.** When a position needs only a few wei of one token, or one unit of liquidity is a visible fraction of the budget (full range at a tiny price), no planner can deploy the whole budget.
- **Uniswap rounds charges up.** Adding liquidity charges up to 2 units more per band and token than the rounded-down prediction. The vault must not pass the deposited amount as a hard `amountMax` without a small margin. Verified against the real `PoolManager` in `test/integration/RealV4Integration.t.sol`.
- **Re-check trust after any external call (M4).** A consumer that checks `isPriceTrusted`, then calls something the depositor controls (a token hook), then values at spot, can be made to credit 50% too much. Re-checking after the callback closes it. Pinned by `test_stale_trust_across_an_external_call_is_exploitable_unless_rechecked`.
- **Deployment check.** `PriceGuard`'s constructor does not verify that the sequencer feed address has code. A typo makes every trust check revert (fail closed, silently, until the first deposit). `PostDeployCheck` must verify the sequencer feed has code and a recent update. Pinned by `test_known_issue_sequencer_address_without_code_bricks_trust_checks_closed`.
- **Feed upgrades.** If a feed's `decimals()` changes, answers fall outside the owner's bounds and trust fails closed until the owner reconfigures the pair.
- **Sandwich ceiling.** While the guard calls a price trusted, a deposit-sandwich gains at most `deposit * m / (1 - m)` for a deviation `m` (about 1.01% of the deposit at the 1% limit), before fees.
- **Test tooling.** `foundry.toml` gained two test-only remappings (`@uniswap/v4-core/` and `solmate/`) so the real v4 `PoolManager` and `StateView` can run in-process. Production code must still not import them; `SrcPolicy` enforces that.

## Found by the M4 audit (see `docs/M4_AUDIT_REPORT.md`)

- **Secret in the repository.** `foundry.toml` contained a BscScan/Etherscan API key in plain text. It now reads `${BSCSCAN_API_KEY}` from the environment, but the key is in the git history and must be rotated.
- **Read-only reentrancy window.** Band storage is updated after the PositionManager call (Slither `reentrancy-eth`). Every state-changing vault function is `nonReentrant` and the PoolManager is locked during settlement, so no funds can move; but a token with transfer hooks could read stale `totalAssets`/`bands` from inside the settlement. Integrators must not read the share price from within token callbacks. Pinned by `test_a_hook_inside_settlement_cannot_reenter_the_vault_or_move_the_price`.
- **ERC-4626 deposits are held idle.** `deposit`/`mint` keep token1 idle until a compounding step (M5) deploys it; idle token1 earns no fees.
- **Single-asset exits depend on the oracle.** ERC-4626 `withdraw`/`redeem` are priced from the pool price and therefore close while PriceGuard does not trust it. Within the tolerance, a manipulator can move the payout by up to about `maxDeviationBps`, as for deposits. The oracle-free exit is M5's pro-rata withdrawal.
- **Deposit size.** Amounts above `uint128` always revert (planning and PositionManager parameters are `uint128`); the `PermitAmountTooLarge` branch is unreachable for that reason. Deposits so small that the 2-units-per-band settlement reserve leaves nothing revert with `ZeroLiquidity`.
- **First-deposit minimum is in raw token1 units.** `MIN_LOCK_SHARES = 1000` and the 10,000 minimum are raw units (0.01 USDC). The inflation attack is still unprofitable (the attacker loses most of any donation), but a victim's rounding loss is up to one share of value rather than one wei; depositors should always pass `minShares`.
- **Permit2 double in tests.** Uniswap's Permit2 is pinned to solc 0.8.17, so the in-process integration tests use `test/integration/utils/Permit2Double.sol`, which implements the same allowance rules; the mainnet fork tests exercise the real Permit2.

## Found by the M5 audit (see `docs/M5_AUDIT_REPORT.md`)

- **Protocol fee when the collector is broken.** A withdrawal never depends on the factory or the fee collector: if the collector is unset, rejects ETH, burns gas, or is blacklisted by the token, the withdrawal's protocol fee stays in the vault for the remaining holders and `ProtocolFeeForfeited` is emitted. The withdrawer is paid from the owed fee either way, exactly per guide 7.2. The other fee paths (`depositPair` after fees accrue, `collectFees`, `compound`) are strict: they revert while the collector cannot be paid, so deposits and compounding pause until governance replaces the collector. That is the intended degraded mode; exits are unaffected.
- **Protocol fee cap.** By team decision (recorded in `IVaultFactory`), the business cap is mutable factory state (`maxProtocolFeeBps`, at most 10,000 bps) rather than the guide's 2,500 constant. The vault therefore only enforces the safety bound: it clamps the factory's `protocolFeeBps` at 10,000 (100 percent of collected fees, never principal) and reads a reverting or malformed factory answer as zero. A fee anywhere up to 100 percent is honoured exactly as configured.
- **Valuation is net of the protocol fee.** `totalAssets` (and everything priced from it: deposits, previews, ERC-4626 exits) values pending fees after the protocol cut, because that is what holders receive when the fees are collected. With an untrusted or reverting factory the cut reads as zero on every path, so valuation and collection still agree.
- **EIP-170 headroom.** `Vault` runtime is 24,118 of 24,576 bytes (`optimizer_runs = 1`, `cbor_metadata = false`). M5 operations live in `VaultM5Module`: `withdrawPair`, `collectFees` and `compound` forward their calldata unchanged by `delegatecall`, and the module reads the vault's immutables back through its public getters. The module is constructor-created and its storage layout is checked slot for slot against `Vault`. Milestone 6 must put the rebalance in a module too.
- **In-kind preview lives on the module.** `VaultM5Module(vault.m5Module()).previewWithdrawPair(vault, shares)` returns exactly what `withdrawPair(shares)` would pay (tested to the wei). There is no wrapper on `Vault` because of EIP-170; the M8 lens should call the module.
- **Compound has no caller-supplied minimum.** `compound` is keeper-only and requires PriceGuard trust; a sandwich within the oracle tolerance can shift the token mix of the compounded amount by at most the tolerance, as for deposits.
- **Read-only reentrancy.** Pair withdrawals and deposit refunds now pay the ERC-20 leg before the native leg, so a native-ETH receiver only sees final state. A token with transfer hooks can still observe intermediate state from inside its own callback; integrators must not read the share price from within token callbacks.
- **Cooldown before milestone 6.** `checkRebalance` reports `COOLDOWN` for 30 minutes after `lastRebalance`, matching the guide's rebalance gate; `lastRebalance` stays zero until M6 sets it.
- **Audit reports restored.** `docs/M2_AUDIT_REPORT.md`, `docs/M3_AUDIT_REPORT.md`, `docs/REAUDIT_M2_M3.md`, `docs/M4_AUDIT_REPORT.md` and `docs/M6_AUDIT_REPORT.md` were referenced here but never committed; they were restored unchanged on 2026-10-23 from the audit sessions that produced them.

## Found by the M6 audit (see `docs/M6_AUDIT_REPORT.md`)

- **EIP-170 headroom is gone again.** `Vault` runtime is 24,559 of 24,576 bytes after M6 (17 bytes left). The M6 audit fixes changed no `Vault` bytecode. Milestone 7 and later must not add code to `Vault`; put new logic in modules.
- **The M6 module comes from the executor.** `Vault`'s constructor takes its rebalance module from `swapExecutor.vaultModule()` (the executor deploys it), so the executor passed to a `Vault` implementation decides the code that runs with the vault's storage. Deployment must use the audited `SwapExecutor` build, and the post-deploy check must assert `executor.factory() == vault.factory()` and `executor.priceGuard() == vault.priceGuard()`: a mismatched factory makes every rebalance swap revert (`UnauthorizedCaller`). There is no room in `Vault` to enforce this on-chain.
- **A manipulated price delays rebalances instead of costing value.** Inside the oracle tolerance an attacker can push the pool against the vault's planned swap far enough that the swap would clear below the oracle floor; the rebalance then reverts (measured: an 80 bps push against a re-centring swap makes even the 1% maximum tolerance refuse). Rebalances that do go through lose at most the keeper's `maxSlippageBps` at the oracle price (measured 9 bps under a 30 bps push against the vault with the 100 bps maximum). Keepers should submit through a private relay (guide 8.4) and retry later.
- **Executor ERC-20 input is pulled, not pushed.** The guide's executor expects the caller to transfer the input first; that design needed an exact-balance check, which let a 1-wei donation block a token's swaps forever. The executor now pulls exactly `amountIn` with `transferFrom` (vault approves the exact amount and resets it to zero afterwards) and verifies the balance delta. Native input is still sent as an exact `msg.value`. The Zap (M9) must follow the same pattern.
- **Partial fills.** An exact-input swap that settles less than `amountIn` refunds the unspent ERC-20 input to the caller. For native input the router would keep unspent ETH; exact-input swaps only settle partially when the pool runs out of liquidity across the whole price range, where the output floor reverts first.
- **`foundry.lock` was missing the Universal Router submodule.** Forge recorded `lib/universal-router` (64027f3) and `lib/v4-periphery` (9969eec) in `foundry.lock` during this audit; the submodule itself is not checked out, and nothing in `src/` or the tests imports it (the in-process router double inherits the pinned periphery's `V4Router`).


## Found by the M7 audit (see `docs/M7_AUDIT_REPORT.md`)

- **First-deposit swap costs stay with the depositor.** When a Normal LP vault's first pair deposit swaps through the executor, the depositor is credited `min(net supplied value, measured value added)`, both at the pre-deposit price and net of fees. The swap's pool fee, price impact and slippage (bounded by the 60% cap and the 1% oracle floor) reduce the depositor's shares, never the existing holders' value. Depositors should always pass `minShares`.
- **A filled lock-on-fill vault is terminal** (guide 9.4). After the `FILLED` rebalance it holds idle tokens, refuses every deposit (`maxDeposit` is 0), and never triggers again; withdrawals keep working. Re-entering the market needs a new vault.
- **The Normal LP first deposit uses `config.centerTick`**, not the live tick. If the price has left that range before the first deposit, the first ladder is minted out of range. The depositor must supply mostly the token that range holds, or the planned swap exceeds the 60% cap (`SwapTooLarge`). The keeper's `OUT_OF_RANGE` rebalance re-centres afterwards. The M8 factory or UI should warn when the configured center is far from the live price.
- **Out-of-range Normal LP rebalances need about a 50% swap.** It fits the 60% cap but must clear the oracle floor (1% plus the pool fee) after price impact, so a vault that is large against pool depth cannot re-centre in one step. Keepers should retry later or split the move; the loss brake is never relaxed.
- **Normal LP cannot plan at raw prices below 2^-96** (tick below about -665,000): the Q96 price rounds to zero and the plan reverts `InvalidPrice`.
- **One-sided ladders keep other-currency fees idle.** Fees a single-token ladder earns in the other currency cannot be added to it. They are part of `totalAssets` and paid out pro rata.
- **An empty pair deposit is refused with `InvalidDepositMode` in every mode.** One-sided vaults used to fail later with `ZeroLiquidity`.
- **EIP-170 headroom.** `Vault` runtime is 24,348 of 24,576 bytes (228 left) after M7 moved first-deposit planning into `VaultM5Module`. The M6 note above about 17 bytes is superseded. New features still belong in modules.
- **CI pins.** The fork job's block (`script/config/mainnet.json`) must be later than every pinned mainnet address's deployment. The Universal Router v2.2.0 was created at block 26,006,366, so the old pin (23,000,000) could never pass. M10 pins the fresh 35-pass replay at block 26,275,306. The job runs under the `fork` profile (the workflow-wide `ci` profile excludes `test/fork`, which silently ran zero tests) and requires zero failures plus the one documented undeployed-M8 skip. `MAINNET_RPC_URL` must be an archive endpoint. The gas snapshot covers deterministic tests only; regenerate with `FOUNDRY_PROFILE=ci forge snapshot --no-match-test "testFuzz|invariant"`. The coverage gate measures `src/` only. The license step checks SPDX headers. Slither reads `slither.config.json`; reviewed false positives are suppressed line by line with the reason next to each `slither-disable-next-line`, and a new High result fails CI.

## M8 factory and governance

- **Production values are intentionally unset.** Governance Safe, executor, guardian, treasury, PriceGuard, ShapeLibrary, deployed M8 addresses, and the production deposit cap remain zero placeholders in `NetworkConfigs.s.sol`. The M8 deployment script rejects required missing values.
- **Nonce-sensitive immutable cycle.** SwapExecutor, Vault, and Factory contain immutable references to each other. The checked deployment sequence predicts the factory's ordinary CREATE address at starting nonce + 7. No transaction may be inserted into that sequence.
- **Two-step delayed completion.** Deployment only nominates the timelock as owner. The Safe must schedule and the restricted executor must execute the three ownership acceptances after the delay.
- **Governance remains powerful.** After delay it may set fees up to 100%, replace the collector, approve keepers/guardian, or choose future strategies and implementations. No fee rate limit was approved. `renounceOwnership` also remains inherited and must not be used operationally.
- **ShapeLibrary constructor identity is not introspectable from Vault.** Vault exposes and actively uses the other custody/oracle/executor dependencies, which Factory verifies. Deployment passes the same ShapeLibrary to Factory, Vault, and strategies; a post-deploy review must preserve that identity.
- **Lens availability flags are mandatory UI inputs.** Failed optional reads are not valid zero balances. Core registry/identity reads still revert for unknown or malformed vaults.
- **No M8 mainnet fork evidence yet.** Final deployed addresses and an archive RPC are required for post-deploy fork verification. See `docs/M8_KNOWN_ISSUES.md`.

## Found by the recheck (see `docs/M7_AUDIT_REPORT.md`, "Recheck")

- **Later deposits and compounding no longer depend on the size of the existing liquidity.** They used to be sized from the token amounts of the bands' stored liquidity, which round down badly when that liquidity is small. A dust first deposit could then block a vault's later deposits and compounds, and so could a full exit or a deposit thousands of times the vault's value. Both now size against a probe-scaled copy of the stored proportions in one module function (`VaultM5Module.depositLiquidity` / `compound`).
- **Keepers must pass `maxSlippageBps >= 1`.** Uniswap rounds every mint up by a wei or two per band, so even a swap-free re-anchor ends a few wei below its starting value and the loss brake refuses it at 0.
- **Trigger widths should exceed the oracle tolerance (M8 factory rule).** A one-sided `trailTicks`, a Normal LP `driftTicks` margin, or a range half-width narrower than PriceGuard's `maxDeviationBps` (in ticks, about 100 ticks at 1%) can be crossed by an in-tolerance price push. A keeper that rebalances at that moment re-anchors the range at the pushed price, and the vault then trades against it when the price returns. The loss per occurrence is bounded by the tolerance, and an attacker must hold the push across the keeper's transaction, but the factory should refuse such configurations.

## Found by the M8 audit (see `docs/M8_AUDIT_REPORT.md`)

- **The deployer owns everything until the handover executes.** Until the timelock accepts ownership (at least 48 hours on mainnet), the deployer can call every owner function on VaultFactory, FeeCollector and PriceGuard. Keep the key offline for the whole window, watch the contracts' events, and run `PostDeployM8Check` with `deploymentOwner` recorded. The check fails if the deployer kept any role, if an ownership transfer is pending, or if the ETH/USDC rule changed. It cannot enumerate every pool rule, keeper or PriceGuard pair set during the window; review those from events.
- **Deploy production through the M11 script, with the Zap.** SwapExecutor's Zap is immutable and VaultFactory pins the executor, so a graph deployed without the Zap can never add it. `DeployM8` refuses mainnet without a Zap address.
- **Safe-based governance uses printed transactions.** When the proposer or executor is a Safe, `ScheduleM8Handover` and `ExecuteM8Handover` print the exact timelock call for the Safe owners instead of broadcasting.
- **A guardian pause takes at least 48 hours to undo** (unpausing is the timelock's). Withdrawals are never paused.
- **Strategy registration does not check the strategy's kind.** Registering, for example, a Buy the Dip strategy under `NormalLP` makes every NormalLP creation revert in the strategy's validator. It is a denial of creation only and is fixed by a corrected `setStrategy`.

## Found by the M9 audit (see `docs/M9_AUDIT_REPORT.md`)

- **The production ETH/USDC oracle tolerance is ten times the guide's default.** `NetworkConfigs` sets `ETH_USDC_MAX_DEVIATION_BPS = 1_000` (10%, the most `PriceGuard` accepts); guide 13.3 recommends 50 bps for major pairs. The tolerance is the bound on every in-tolerance sandwich (deposits, rebalances and zaps lose up to about `maxDeviationBps + maxSlippageBps`). On a mainnet fork, a push to the edge of the 10% tolerance cost a 50,000 USDC zapper 1.36% (`test_realPoolSandwichedZapStaysInsideTheConfiguredBound`). Set the production value (M11) deliberately, with the liveness trade-off: a tighter tolerance also refuses honest operations while the feed lags the pool.
- **The Zap pins its three strategy contracts.** A vault created under a newly registered strategy deployment is refused (`UnsupportedStrategy`). Supporting it needs a new Zap, which needs a new SwapExecutor (its Zap is immutable), which needs a new VaultFactory (it pins the executor).
- **The split leaves part of the input to refund.** It follows the guide 8.3 formula, which buys the full token0 shortfall measured before the fee, so about `fee / 2` of the input comes back (0.025% on a 0.05% pool, 0.15% at 0.3%, 0.5% at 1%). The split is also priced before the zap's own swap moves the price, so concentrated ladders refund more as the zap grows. In total, in the 0.05% test pool with a 12%-wide ladder: 0.026% of a 100 USDC zap, 0.05% at 1,000, 0.29% at 10,000 and about 1.1% at 40,000. Both parts are returned to the caller in the same transaction, as guide 11.2 allows. On a first deposit the vault's own plan swaps the remainder instead.
- **A wrong-token zap can close a one-sided vault's deposit window.** When the ladder sits at the price, the zap's own swap can push the price into it, and the deposit reverts with `DepositNotAllowed` (atomically; the caller keeps everything).
- **`quoteZap` is an estimate.** It does not check PriceGuard trust, and dust inputs it quotes can still revert in `zapDeposit` (`ZeroLiquidity`, `FirstDepositTooSmall`, or a swap of a few raw units whose rounded output misses the 1% floor). It never quotes more than an immediate zap mints.
- **Anything sent to the Zap outside a zap stays there.** Direct token transfers, forced ETH, and a vault withdrawal or deposit with the Zap as receiver are isolated by the balance snapshots and never paid out; there is no sweep function.
- **Contract callers must accept ETH refunds on native pools.** Leftover ETH is returned to the caller in the same transaction; a caller that rejects ETH cannot zap there.

## M10 static-analysis dispositions

- **Informational — VaultLens zero-share equality.** Slither's sole Medium/High-confidence result flags `position.shares == 0`. This is an intentional read-only fast path, cannot influence pricing or authorization, and returns the correct zero position. Mitigation: keep the Lens non-authoritative and preserve tests for zero and unavailable accounting.
- **Informational — guarded module callbacks.** Slither cannot propagate the Vault's external `nonReentrant` guard through its internal deposit helper or delegated M5/M6 module calls. Impact without the guard would be stale balance reuse; every token-moving external Vault entry point is guarded, direct module calls are rejected, and callback attack tests plus the 1,000x128 invariants passed. Narrow source annotations record this proof.
- **Informational — registered native-value destination.** Slither cannot retain Zap's factory-registry validation across `_deposit`. The destination is always a factory-created Vault validated by `_validatedVault`; an arbitrary user address cannot reach the call. Factory-validation and malicious-vault tests are the mitigation.
- **Low — bounded atomic loops and token analyzer warnings.** Aderyn reports two Low categories in Zap. Loops are capped at five bands and must revert atomically on a malformed plan. Transfers use SafeERC20/Permit2 and measured deltas. Residual impact is bounded transaction failure, not silent asset loss.
